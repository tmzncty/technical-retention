## Case 138 — Redis 2.6 AOF rewrite / current-state re-serialization findings

Grounding record: [`evidence/138-redis26-aof-rewrite-grounding.md`](evidence/138-redis26-aof-rewrite-grounding.md).

- **2929 — Redis 2.6.0 release floor != invention priority:** the annotated `2.6.0` tag dated 22 October 2012 anchors the inspected released behavior, but does not establish first invention of AOF, command logging, rewrite, or background compaction. (`H/P`, `X`)
- **2930 — replayable AOF history != current in-memory dataset:** the append file records executable write commands while the live dataset is their current accumulated result; they are different retained representations of related state. (`H/P`, `E`)
- **2931 — AOF replayability != complete event-history preservation:** startup can rebuild Redis state by executing the retained command stream, but later rewrite is allowed to replace that stream with a different state-producing sequence. (`H/P`, `E`)
- **2932 — AOF rewrite != old-log record filtering:** Redis 2.6 `rewriteAppendOnlyFile()` iterates the current dataset and emits reconstruction commands instead of scanning the old AOF and selecting surviving records. (`H/P`, `E`)
- **2933 — current-state reconstructability != command-sequence identity:** multiple historical mutations can collapse into a shorter replacement representation while the resulting dataset remains recoverable. (`H/P`, `E`)
- **2934 — fork-time dataset image != final concurrent state:** the rewrite child serializes its fork-time view while the parent remains able to process later mutations. (`H/P`, `E`)
- **2935 — post-fork rewrite buffer != rewritten base:** parent-side difference buffering preserves changes that the child snapshot cannot contain; the base and delta have complementary handoff roles. (`H/P`, `E`)
- **2936 — same command encoding != same retention role:** during BGREWRITEAOF a mutation can feed both the ordinary AOF path and the rewrite-difference buffer, even though one belongs to current append persistence and the other to temporary replacement closure. (`H/P`, `E`)
- **2937 — child rewrite success != authoritative replacement AOF:** the parent must still append accumulated differences and complete the rename/file-descriptor switch before the new file becomes the configured append target. (`H/P`, `E`)
- **2938 — failed rewrite != intentional replacement of the old recovery representation:** child/merge/rename failure follows cleanup/error paths instead of promoting the failed temporary product; this does not prove unrelated recent writes durable. (`H/P`, `E`, `X`)
- **2939 — BGREWRITEAOF start/scheduling != rewrite completion:** accepting or scheduling the maintenance operation is distinct from later successful result installation. (`H/P`, `E`)
- **2940 — AOF-file growth trigger != payload-retention deadline:** automatic rewrite is driven by current AOF size relative to remembered post-rewrite/startup size plus a minimum-size threshold, not by key age or medium decay. (`H/P`, `E`, `X`)
- **2941 — append-history growth != logical-dataset growth:** repeated updates to existing state can expand the AOF without proportionally expanding the current dataset, which is why state-based rewrite can reduce the carrier. (`H/P`, `E`)
- **2942 — rewrite policy != fsync durability policy:** `auto-aof-rewrite-*` decides when history is re-serialized while `appendfsync no/everysec/always` separately controls ordinary append synchronization. (`H/P`, `E`)
- **2943 — background maintenance can widen foreground durability exposure:** `no-appendfsync-on-rewrite` explicitly allows a latency/throughput trade in which fsync is suppressed during BGSAVE/BGREWRITEAOF, so maintenance is not automatically neutral to concurrent write-retention guarantees. (`H/P`, `E`)
- **2944 — absolute expiration representation != original TTL-command history:** Redis rewrites/feeds several expiration forms as `PEXPIREAT`, retaining the current absolute deadline relation without retaining the exact earlier relative command form. (`H/P`, `E`)
- **2945 — sync-temp + rename switch != universal crash-durability theorem:** Redis 2.6 documents and implements an atomic-intended replacement sequence, while Case 124 prevents upgrading that application protocol into a claim about every filesystem/device/power-failure model. (`H/P`, `A`, `X`)
- **2946 — old-AOF retirement != media sanitization:** replacing/unlinking/closing the former AOF ends its Redis recovery authority but does not prove overwrite, Flash erase, crypto erase, or forensic disappearance. (`E`, `X`)
- **2947 — Redis AOF rewrite != Kafka keyed compaction != LevelDB MANIFEST recovery:** all can reduce detailed retained history while preserving continuation, but Redis 2.6 re-serializes current dataset state, Kafka 0.8.1 filters keyed log records while preserving offsets, and LevelDB keeps user WAL separate from metadata-history/current-file-set reconstruction. (`A`, `X`)
- **2948 — related-repository boundary:** fresh `computing-archaeology` searches for Redis AOF / BGREWRITEAOF found no dedicated overlap; broad Redis persistence genealogy, earliest implementations, RDB/AOF evolution, and Redis 7 multipart AOF belong there if developed. (`H/P` project-state record)
