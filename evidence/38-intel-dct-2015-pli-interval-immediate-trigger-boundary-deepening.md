# Case 38 Deepening — Intel DCT 2015 PLI Interval / Immediate-Test Boundary

## Status

**`bounded deepening complete`**

This note deepens [`../cases/38-intel-dc-s3700-pli-self-test-validation.md`](../cases/38-intel-dc-s3700-pli-self-test-validation.md) without changing Case 38's maturity.

The narrow question is:

> Once the S3700/S3500 capacitor-test cadence is exposed through Intel's management tooling, is `PLITestTimeInterval` merely a stored interval value, or does changing that apparent policy state also carry an immediate maintenance-action semantic?

The September-2015 Intel SSD Data Center Tool 2.3.x user guide gives a surprisingly sharp answer. For the S3700/S3500 management surface it exposes a vendor-unique PLI capacitor-test interval, but the documented values do not encode only a duration. Values `1` through `6` also say `do immediate test`; value `0` says `no immediate test`. In particular, values `0` and `1` both have a **0-minute interval** while differing in the immediate-test semantic.

That establishes a useful boundary:

```text
maintenance cadence value
    !=
immediate maintenance-action request

one management property
    can encode both
```

It also exposes a control-plane projection boundary. The underlying S3700 product specification names vendor SCT Feature Control code `D000h`; period SCT Feature Control semantics separately carry feature state and persistence-related option flags. The Intel DCT 2.3.x user-facing syntax, however, documents only `PLITestTimeInterval=(0-6)`. The inspected DCT documentation does not expose the lower-level persistence option as a separate CLI argument.

Therefore:

```text
low-level protocol control dimensions
    !=
management-tool control dimensions visible to an operator
```

This note does **not** prove the exact raw SCT command bytes generated by DCT, the persistence horizon selected by DCT, whether an immediate test completes before the CLI returns, or how an interrupted immediate test is recovered.

## 1. Source custody and chronology

### 1.1 October-2012 Intel S3700 product specification — manufacturer-primary feature identity

Intel Corporation, _Intel Solid-State Drive DC S3700 Product Specification_, order `328171-001US`, October 2012:

<https://download.intel.com/newsroom/kits/ssd/pdfs/Intel_SSD_DC_S3700_Product_Specification.pdf>

The product specification places `D000h` under SCT Feature Control and names it `Power Safe Write Cache capacitor test interval`.

This is the product-level anchor for the feature identity. It does not publish the `0`–`6` management encoding used by the later Data Center Tool.

### 1.2 September-2015 Intel SSD Data Center Tool 2.3.x guide — period manufacturer document, third-party surviving custody

Intel Corporation, _Intel Solid State Drive Data Center Tool User Guide_, document `331961-005US`, September 2015, Software Version 2.3.x.

A searchable surviving copy was inspected at:

<https://www.scribd.com/document/523644939/Intel-SSD-Data-Center-Tool-2-3-x-User-Guide-331961-005>

The document itself identifies Intel as publisher, gives document number `331961-005US`, copyright 2015 Intel Corporation, and a revision history whose revision `005` is dated September 2015 for tool version 2.3.0.

The custody limitation is explicit: this surviving copy is hosted by Scribd rather than an Intel-controlled domain. It is used as a **period manufacturer-document witness with third-party custody**, not silently upgraded to Intel-hosted archival custody.

The guide's introductory feature list says the following functionality applies to the **Intel SSD DC S3700 and Intel SSD DC S3500 Series only**, including SCT Feature Control for `PLI Cap test time interval (vendor unique)`. Its supported-drive list separately includes the S3700.

The guide's property tables document `PLITestTimeInterval` for ATA devices with values:

```text
0 -> 0 min, no immediate test
1 -> 0 min, do immediate test
2 -> 60 min, do immediate test
3 -> 1440 min, do immediate test
4 -> 4320 min, do immediate test
5 -> 10080 min, do immediate test
6 -> 20160 min, do immediate test
```

The `set` command accepts exactly one property at a time and documents `PLITestTimeInterval=(0-6)` as one such configurable property.

### 1.3 August-2019 Intel-hosted DCT 3.0.20 guide — later first-party custody corroboration

Intel Corporation, _Intel Solid State Drive Data Center Tool User Guide_, document `331961-020US`, August 2019, Software Version 3.0.20:

<https://www.intel.com/content/dam/support/us/en/documents/memory-and-storage/Intel_SSD_DCT_3_0_x_User_Guide.pdf>

This later Intel-hosted PDF still lists the S3700 among supported SSDs and preserves the same `PLITestTimeInterval` value semantics in both the `show` property and configurable `set` property tables.

This source is used as **later first-party continuity/corroboration**, not as evidence that every 2019 tool behavior existed unchanged in every 2012 S3700 firmware revision.

The source roles are therefore kept separate:

```text
2012 S3700 product spec
    -> product feature identity D000h

2015 Intel DCT manufacturer document
    -> period S3700/S3500 management-tool exposure and value semantics

2019 Intel-hosted DCT guide
    -> later first-party custody corroboration of the same management encoding
```

## 2. Historical / interface record

### 2.1 DCT exposes the PLI test cadence as a named management property

The 2015 DCT guide says the S3700/S3500-specific feature set includes the vendor-unique PLI capacitor-test time interval. The general command summary exposes:

```text
set ... -intelssd (Index) PLITestTimeInterval=(0-6)
```

and the detailed property table says this changes the device's PLI test-time interval setting.

Thus the low-level `D000h` feature is no longer only a product-specification capability by 2015; Intel also exposes it through an operator-facing production-management CLI.

That is historical/interface evidence. It does not by itself say how DCT constructs the underlying ATA/SCT request.

### 2.2 The property value is not a pure duration

The key table is not a simple mapping from an integer to minutes.

Two encodings share the same interval:

```text
0 -> 0 minutes + no immediate test
1 -> 0 minutes + do immediate test
```

The remaining nonzero cadence values likewise include `do immediate test`.

Therefore a representation such as:

```text
PLITestTimeInterval = 2
```

cannot be understood only as:

```text
future cadence = 60 minutes
```

because Intel documents an additional immediate-test semantic in the same encoded choice.

The strongest source-grounded statement is:

> **The documented DCT property encoding carries both interval information and an immediate-test semantic.**

The documentation does not say that the immediate-test semantic is a separately stored bit, a one-shot command internally, or a persistent field. Those are implementation questions.

### 2.3 A zero-minute interval still has two distinct operator meanings

Values `0` and `1` are especially useful evidence because they rule out an interpretation in which the property code is merely a compressed duration enumeration.

Both represent `0 min`, but only one says `do immediate test`.

So:

```text
same documented interval component
    !=
same command meaning
```

This is stronger than merely observing that some interval choices happen to trigger maintenance. The table itself demonstrates an independent immediate-action distinction at the management interface.

### 2.4 “Modify one setting” does not imply “change one semantic dimension”

The DCT guide says device modification changes one configurable setting at a time. `PLITestTimeInterval` is one property for that purpose.

But the value table shows why a management API's **property count** should not be mistaken for a count of independent semantic dimensions:

```text
one property assignment
    -> cadence component
    + immediate-test semantic
```

That is a useful historical warning for reconstructing older management interfaces: a single named knob may package policy and action together.

### 2.5 `show` and `set` expose the same coded value space, but that does not prove action replay

The DCT guide documents the same `0`–`6` meanings in the property shown by `show` and in the property accepted by `set`.

This creates a subtle boundary. The visible value can describe a setting whose documented meaning includes `do immediate test`, but the guide does not say that merely **reading** the value initiates a test, nor that a previously stored code necessarily retriggers a test whenever it is observed or restored.

Therefore:

```text
reported configuration code
    !=
new maintenance execution event
```

and:

```text
setting a code with immediate-test semantics
    !=
proof that later reads/reboots replay that action
```

The action boundary must be attached to the documented modification semantics, not inferred from the existence of the code alone.

## 3. Engineering reconstruction — policy, trigger, execution, and evidence are different state classes

### 3.1 A maintenance-control write can have both declarative and imperative effects

The engineering reconstruction suggested by the DCT table is:

```text
host writes PLITestTimeInterval value
        |
        +-> future cadence policy
        |
        +-> immediate-test request/effect (for documented values 1..6)
```

The first branch is declarative: it concerns when testing should recur.

The second branch is imperative: it concerns a test to occur now/immediately in connection with the setting operation.

The source does not expose the firmware's exact internal transaction graph, so `request/effect` is deliberately broader than a claim about one internal queue entry.

### 3.2 Cadence policy is not test execution

Case 38 already distinguishes PLI hardware from readiness evidence. This slice adds another boundary:

```text
configured cadence
    !=
immediate-test request
    !=
test started
    !=
test completed
    !=
test passed
    !=
AFh updated durably
    !=
future real power-loss transfer succeeds
```

An operator who sees a successful `set` command has not thereby observed all later stages.

The DCT guide documents the setting semantics, not an end-to-end completion protocol for the capacitor test.

### 3.3 Trigger provenance can matter to telemetry interpretation

If a readiness test can occur because an operator changes `PLITestTimeInterval`, then a later change in AFh or in `minutes since last test` may have more than one possible scheduling provenance:

```text
periodic scheduler due event
    OR
management operation with immediate-test semantics
    OR
other manually invoked path documented elsewhere
```

That is an engineering inference about observability. It is **not** a claim that AFh records which provenance occurred. The inspected sources do not show a provenance field.

A telemetry system that needs to explain why a readiness test happened should therefore avoid treating `last test` state as self-describing provenance unless another log or management record supplies that relation.

### 3.4 Low-level persistence policy and high-level DCT syntax are separate control planes

The existing Case 38 cadence-persistence deepening establishes a protocol-level distinction around SCT Feature Control:

```text
current feature state
    !=
last nonvolatile feature state

state value
    !=
persistence option
```

The DCT 2.3.x CLI syntax shown here exposes only:

```text
PLITestTimeInterval=(0-6)
```

The inspected DCT guide does not document a second CLI argument for SCT Feature Control's volatile-versus-preserved option.

That means the operator-facing projection is narrower than the generic low-level command envelope:

```text
SCT Feature Control
    [feature code, state, option semantics, ...]
        |
        v
DCT management property
    [PLITestTimeInterval = 0..6]
```

What DCT chooses for any hidden/lower-level option is **not established here**.

This matters because management-tool convenience can conceal state-lifetime dimensions that exist at a lower protocol layer.

### 3.5 A hidden persistence choice cannot be inferred from tool convenience

It would be tempting to reason:

> “Because DCT presents `PLITestTimeInterval` as a normal configurable property, the setting must persist across power cycles.”

The inspected documentation does not justify that conclusion.

The correct separation is:

```text
property is configurable through DCT
    !=
DCT requests nonvolatile persistence
    !=
S3700 firmware accepts that persistence mode for D000h
    !=
setting experimentally survives reset/power loss
```

The earlier cadence-persistence evidence debt therefore remains open at the device-experiment level.

## 5. Historical record versus engineering reconstruction

### Historical record

The directly documentable facts are:

- Intel's October-2012 S3700 specification names `D000h` as the power-safe-write-cache capacitor-test interval.
- Intel's September-2015 DCT guide says S3700/S3500-specific tool functionality includes the vendor-unique PLI capacitor-test interval.
- The DCT guide exposes `PLITestTimeInterval=(0-6)`.
- The value table gives both an interval and an immediate-test semantic.
- Values `0` and `1` both specify a 0-minute interval but differ on whether an immediate test is requested.
- Intel's later Intel-hosted 2019 DCT guide preserves the same encoding and still lists S3700 as a supported drive.

### Engineering reconstruction

The repository reconstructs those facts as evidence that:

- maintenance policy and immediate maintenance action are different semantic dimensions even when packed into one management property;
- successful configuration is not equivalent to completed maintenance;
- maintenance execution is not equivalent to retained evidence of its result;
- management tooling can project only part of a lower-level protocol's state-lifetime controls;
- interpreting readiness telemetry may require provenance outside the telemetry field itself.

These are engineering categories used by this repository, not Intel's historical vocabulary.

## 7. Philosophical interpretation — a rule and an occurrence are not the same retained thing

A bounded interpretation is:

> Technical systems can retain a rule about when evidence should be regenerated while separately producing events that regenerate the evidence; an interface may package both acts into one apparent setting.

That yields a layered relation:

```text
retain maintenance policy
    !=
retain evidence that maintenance occurred
    !=
retain evidence that maintenance succeeded
```

and, for this specific interface:

```text
change policy
    can also request maintenance now
```

The project may call this a distinction between **declarative maintenance state** and **imperative maintenance transition**, but those are analytical terms. Intel's documents do not use that philosophical vocabulary.

The limit is important: nothing here supports a claim that one configuration value is a metaphysical “memory of intention,” or that all device settings should be decomposed this way. The source supports one bounded interface relation.

## 9. What this closes

This slice closes the narrow Case 38 debt:

> **Does the operator-facing PLI cadence control represent only future scheduling policy?**

No. Period Intel DCT documentation for the S3700/S3500 management surface shows that its coded property also carries an immediate-test semantic; codes `0` and `1` prove that the immediate-test distinction is not reducible to the interval duration alone.

It also closes a second bounded documentation question:

> **Does the DCT user-facing syntax expose the same persistence-choice dimension that surrounds SCT Feature Control at the lower protocol layer?**

Not in the inspected syntax. The guide exposes `PLITestTimeInterval=(0-6)` but does not document a separate volatile/preserved option for that property.

## 10. Remaining evidence debt

The next useful slices are now narrower:

1. **Raw DCT-to-SCT trace:** capture or source-code/firmware evidence showing exactly which SCT Feature Control state and option flags DCT emits for each `PLITestTimeInterval` value.
2. **Completion boundary:** determine whether DCT waits for the immediate PLI test to finish, merely initiates it, or observes a later status path.
3. **AFh publication ordering:** determine when result, minutes-since-test, and lifetime-test-count become authoritative relative to test completion and command return.
4. **Reset/power interruption:** interrupt a DCT-triggered test at controlled phases and observe D000h/AFh behavior after restart.
5. **Persistence experiment:** read D000h-equivalent state before and after soft reset, hard reset, and full power cycle under known option semantics.
6. **Provenance observability:** determine whether any product log distinguishes periodic, manual, and configuration-triggered PLI self-tests.
7. **Custody improvement:** recover an Intel-hosted or archived Intel-origin copy of `331961-005US`; until then, keep the 2015 period document's custody grade distinct from the Intel-hosted 2019 corroboration.

Until those exist, Case 38 should remain `grounded`, not promoted.
