# Evidence 09 — Micron 1999 SDRAM AUTO REFRESH vs SELF REFRESH control-boundary deepening

**Status:** `bounded deepening complete`

**Parent case:** [`../cases/09-dram-cbr-refresh-address-internalization.md`](../cases/09-dram-cbr-refresh-address-internalization.md)

**Bounded question:** after refresh-row enumeration had already moved on-chip in CAS-before-RAS DRAM, what additional retention-control function had moved on-chip by the late-1990s SDRAM product boundary, and what still remained an external-controller obligation?

This record is intentionally narrow. It does **not** attempt a general SDRAM history, a JEDEC standard genealogy, a first-invention claim, or a DDR/per-bank-refresh history.

---

## Why this slice matters

Case 09 already established a 1980s separation:

```text
refresh deadline
    != refresh request cadence
    != refresh-row enumeration
    != row restoration
```

In TI's 1984-filed design, an on-chip refresh counter can supply the refresh row while an external processor or controller still determines how often the CAS-before-RAS request occurs.

A later SDRAM product gives a useful controlled successor comparison because its own documentation places two refresh modes next to one another:

```text
AUTO REFRESH
SELF REFRESH
```

The useful question is not whether both modes "refresh DRAM." The useful question is which parts of the maintenance-control chain are internal in each mode.

## Historical record

### H/P — 1999 Micron describes AUTO REFRESH as analogous to conventional CBR refresh

On printed page 13 of the November-1999 datasheet, Micron states that `AUTO REFRESH` is used during normal SDRAM operation and is analogous to CAS-before-RAS refresh in conventional DRAM.

This is unusually valuable for Case 09 because the manufacturer itself supplies the comparison between the older asynchronous-DRAM operation and the SDRAM command.

The evidence supports:

```text
CBR refresh and SDRAM AUTO REFRESH
    = historically compared by Micron at the operation-class level
```

It does **not** support:

```text
identical signaling
identical internal circuit
identical controller interface
simple TI -> Micron implementation genealogy
```

### H/P — AUTO REFRESH remains a nonpersistent externally issued request

The same 1999 paragraph says the AUTO REFRESH command is `nonpersistent` and must be issued each time refresh is required.

For the documented 64 Mb device family:

- refresh addressing is generated by the internal refresh controller;
- the address bits are `Don't Care` during AUTO REFRESH;
- 4,096 AUTO REFRESH cycles are required within 64 ms;
- a distributed schedule of one command every 15.625 µs satisfies that requirement;
- alternatively, the commands can be burst within the refresh window.

The bounded control partition is therefore:

```text
AUTO REFRESH
external system/controller
    -> supplies repeated refresh commands / cadence
DRAM
    -> supplies refresh addressing
    -> performs row refresh
```

This preserves the central Case-09 result from the 1980s while changing the command interface.

### H/P — SELF REFRESH changes the cadence authority after mode entry

The adjacent 1999 `SELF REFRESH` paragraph says the command can retain data even if the rest of the system is powered down and that the SDRAM retains data without external clocking.

Entry is described as being like AUTO REFRESH except CKE is disabled low. After the command has been registered:

- other SDRAM inputs become `Don't Care` except CKE;
- CKE must remain low;
- the SDRAM provides its own internal clocking;
- that internal clocking causes it to perform its own AUTO REFRESH cycles.

This is direct manufacturer evidence for a different control partition:

```text
SELF REFRESH entry
external system/controller
    -> requests entry and maintains the required mode condition
DRAM
    -> supplies internal clocking
    -> schedules its own refresh activity while in the mode
    -> supplies refresh addressing
    -> performs row refresh
```

The word `self` therefore has a product-level mechanism here that differs materially from the TI patent's earlier title phrase `self refresh circuitry`, where the patent explicitly leaves request frequency outside the DRAM.

### H/P — AUTO REFRESH and SELF REFRESH share the row refresh counter

The 1999 datasheet states that, after leaving self-refresh mode, AUTO REFRESH commands must again be issued at the specified interval because both SELF REFRESH and AUTO REFRESH use the row refresh counter.

This is important because it shows that two distinct scheduling-authority regimes can share part of the same maintenance-control state.

The shared counter does not collapse the modes into one control contract.

### H/P — exit from SELF REFRESH is a handoff, not proof that maintenance ceased instantly

Micron requires the external clock to be stable before CKE returns high and requires NOP commands during `tXSR` because an internal refresh may still be in progress.

The evidence therefore supports a mode-transition boundary:

```text
exit requested
    != internal refresh necessarily already complete
    != normal command service immediately available
```

After the exit interval, responsibility for ordinary AUTO REFRESH cadence returns to the external system/controller.

### H/P — later product-family documentation preserves the same distinction

A later Micron-authored revision of the same 64 Mb family (`Rev. V 09/14`) again states that:

- AUTO REFRESH is nonpersistent;
- address generation is internal;
- SELF REFRESH retains data without external clocking;
- after entry, the device provides its own internal clocking and performs its own AUTO REFRESH cycles;
- both modes use the row refresh counter.

This later revision is a continuity witness for the product-family documentation, not a substitute for the 1999 date anchor.

## Engineering reconstruction

### E — internal refresh addressing and internal refresh scheduling are separate design properties

The strongest bounded result is now directly product-comparative rather than merely terminological.

For Micron's documented SDRAM:

```text
AUTO REFRESH
internal row enumeration
external repeated-command cadence

SELF REFRESH
internal row enumeration
internal recurring refresh clock/cadence after entry
```

Therefore:

> **internal refresh addressing != autonomous refresh scheduling.**

The two properties can coexist or be separated by mode in the same device.

### E — "autonomous" must be scoped to the maintenance episode

SELF REFRESH is not evidence that the DRAM is independent of the system in every sense.

The system still participates by:

- placing the DRAM into the mode;
- satisfying the documented entry conditions;
- maintaining CKE low while the mode is active;
- restoring a stable clock and satisfying `tXSR` on exit;
- resuming external AUTO REFRESH commands after return to normal operation.

So the defensible statement is:

> **refresh-cycle recurrence is autonomous within the entered self-refresh regime.**

Not:

> **the DRAM is globally autonomous.**

### E — one retained maintenance counter can serve multiple authority regimes

Because both AUTO REFRESH and SELF REFRESH use the row refresh counter, the counter's current phase belongs to neither the host nor one mode exclusively.

A useful decomposition is:

```text
maintenance-control state
    row-refresh-counter phase

maintenance-command authority
    external in AUTO REFRESH

maintenance-cadence authority
    external in AUTO REFRESH
    internal during SELF REFRESH
```

This sharpens the repository rule:

> **where control state is stored != who currently has authority to advance maintenance.**

### E — mode entry converts a repeated external obligation into a retained regime

AUTO REFRESH is explicitly nonpersistent: the command must recur.

SELF REFRESH is different at the interface. One entry command places the device into a mode in which refresh recurrence continues internally until exit.

This gives a bounded distinction between:

```text
repeated maintenance request
    vs
retained maintenance regime
```

The mode itself is not application history. It is a control condition that changes who is responsible for the recurrence needed to retain payload.

### E — a maintenance handoff has entry, steady-state, and exit semantics

A simple phrase such as `refresh moved on-chip` hides three different stages:

```text
entry
    external command establishes the regime

steady state
    internal clocking drives recurring refresh work

exit
    internal work may still be completing;
    external timing/commands re-assume responsibility afterward
```

Thus a maintenance-control migration is not necessarily a permanent architectural transfer. It can be a reversible mode-dependent handoff.

## Functional comparison to the 1980s Case-09 evidence

### A — same broad retention obligation, different control partition

The comparison is functional and bounded:

```text
TI 1984-filed CBR-counter design
    internal refresh-row enumeration
    external processor/controller controls request frequency

Micron 1999 SDRAM AUTO REFRESH
    internal refresh-row enumeration
    external system/controller must issue each refresh command

Micron 1999 SDRAM SELF REFRESH
    internal refresh-row enumeration
    internal clocking drives recurring refresh after mode entry
```

This is not a proof of design descent or direct influence.

### A — the historical word `self refresh` changes technical content across sources

The TI patent title contains `Self refresh circuitry for dynamic memory`, but its own description leaves the refresh-request frequency external.

Micron's 1999 product documentation uses `SELF REFRESH` for a mode in which the SDRAM supplies its own internal clocking and performs recurring refresh cycles without external clocking.

Therefore:

```text
same historical phrase
    != same distribution of retention work
```

The correct method is mechanism-first interpretation, not vocabulary-first equivalence.

### A — Case 10 remains a different question

Case 10 asks how a device may derive refresh cadence from leakage or temperature-related conditions and where that policy authority lives.

This Evidence 09 asks a simpler control-locus question:

```text
who supplies recurring refresh cadence at all?
```

Micron 1999 does not by itself establish leakage tracking, temperature compensation, retention-aware scheduling, or per-row retention policy.

## Philosophical interpretation

### I — persistence can depend on a reversible transfer of maintenance responsibility

The exact technical fact is that the same payload-retention obligation can be discharged under two different control regimes in one device.

AUTO REFRESH leaves repeated maintenance requests outside the DRAM. SELF REFRESH retains a mode in which recurrence proceeds internally.

This supports a narrow conceptual point:

> apparent persistence may depend not only on continuing work, but on a maintained allocation of responsibility for initiating that work.

The interpretation stops at the mechanism. It does not make self-refresh a metaphor for social autonomy, memory, or agency.

### I — a stable interface name can conceal a change in authority

Both modes ultimately refresh the same dynamic array and share a refresh counter, yet the recurrence authority differs.

That makes `refresh` too coarse as a conceptual category unless the analysis specifies:

- trigger;
- scheduler/cadence authority;
- enumerator;
- executor;
- mode-transition responsibility.

## Explicit non-claims

This record does **not** establish any of the following:

1. Micron invented SDRAM SELF REFRESH.
2. November 1999 is the first commercial appearance of SDRAM SELF REFRESH.
3. TI's 1984 patent is a direct ancestor of Micron's 1999 implementation.
4. Micron's internal refresh controller is transistor-for-transistor related to TI's disclosed circuit.
5. `AUTO REFRESH` and conventional CBR refresh use identical signaling.
6. `SELF REFRESH` means the device requires no external power.
7. The internal self-refresh clock is identified here as a particular oscillator topology.
8. The 1999 device performs temperature-compensated or leakage-tracked refresh.
9. The datasheet proves every row is physically refreshed correctly under silicon faults.
10. Sharing a row refresh counter means AUTO REFRESH and SELF REFRESH have identical control semantics.
11. Entry into SELF REFRESH proves an internal refresh cycle starts immediately at that same edge.
12. Exit from SELF REFRESH proves no internal refresh remains in progress; the documented `tXSR` requirement blocks that shortcut.
13. The 2014 revision proves every sentence was unchanged in every intervening revision.
14. A product datasheet establishes the normative wording or introduction date of a JEDEC SDRAM standard.
15. This slice establishes DDR, DDR2, DDR3, DDR4, LPDDR, or per-bank-refresh semantics.
16. Internalizing recurrence makes the underlying DRAM cell nonvolatile.
