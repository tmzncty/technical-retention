# Evidence Record 17 — RAID Parity Reconstruction, 1977–1994

## Purpose

This record grounds [`cases/17-raid-parity-reconstruction-degraded-repair.md`](../cases/17-raid-parity-reconstruction-degraded-repair.md).

The bounded claim is not “RAID makes disks reliable.” It is narrower:

> **Parity/checksum coding can preserve the recoverability of one missing disk contribution without preserving a full duplicate, while correct degraded operation and return to the intended redundancy condition depend on validity/currentness meta state, reconstruction progress, spare/replacement capacity, and completion of repair.**

The record also controls a common historical error: the 1987–1988 Berkeley RAID name/taxonomy must not be turned into a claim that parity-based multi-device recovery began there. Norman Ken Ouchi’s IBM filing from 1977 directly describes an XOR/check-sum reconstruction mechanism across failure-independent storage units.

## Source A — Norman Ken Ouchi / IBM, US4092732A

### Bibliographic / provenance record — H/P

- **Title:** `System for recovering data stored in failed memory unit`
- **Inventor:** Norman Ken Ouchi
- **Original assignee:** International Business Machines Corporation
- **Filed:** 31 May 1977
- **Published:** 30 May 1978
- **Publication:** US4092732A
- **Direct source:** <https://patents.google.com/patent/US4092732A/en>

The patent record directly supplies the date, inventor, and IBM assignment.

### Duplicate storage is identified as a straightforward but expensive alternative — H/P

The description first discusses keeping a duplicate set of storage devices and a duplicate file of all data. It notes the storage-cost and update overhead of that approach.

**Anchor:** Google Patents HTML, definition/description lines corresponding to the discussion immediately preceding the segmented-record scheme; in the current indexed rendering, around lines 75–77.

**Use:** establishes that the patent itself distinguishes full duplication from the later disclosed checksum reconstruction arrangement.

### Record segmentation + XOR `check sum` — H/P

The disclosed mechanism divides a record into segments. With five memory units, the example uses four equal record segments. A same-length `check sum` is generated by `Exclusive Oring` the record segments.

**Anchor:** current indexed rendering around lines 78–80.

### Failure-independent placement — H/P

The record segments and the check-sum segment are stored on different `failure independent memory units`.

**Anchor:** current indexed rendering around lines 80–87.

### Recovery of one unavailable contribution — H/P

During recovery, the accessible segments and the check-sum segment pass through the check-sum generator, producing the unavailable system-record segment; the reconstructed segment is then placed in memory for normal processing.

**Anchor:** current indexed rendering around lines 164–166.

### Disk embodiment + placement directory — H/P

The preferred description uses a storage subsystem containing a drive controller and a string of disk drives. It also describes a directory that identifies the physical storage location of record segments.

**Anchors:** current indexed rendering around lines 93–104 and 141–146; Figure 6 is described as the directory used to keep track of where record segments are physically stored.

### What Source A establishes

- multi-device data segmentation;
- XOR/check-sum redundancy;
- one-device-loss reconstruction in the bounded arrangement;
- the fact that this mechanism is distinct from simply keeping a duplicate file;
- a 1977 priority boundary earlier than the Berkeley `RAID` name.

### What Source A does **not** establish

- the term `RAID`;
- RAID 3/4/5 naming;
- that Ouchi invented every parity-array idea;
- modern rebuild scheduling, scrubbing, distributed spare policy, or RAID-6/P+Q;
- a direct historical genealogy from this patent to each later RAID product.

The patent is used as a mechanism/prior-art boundary, not as a universal invention claim.

## Source C — Chen, Lee, Gibson, Katz, Patterson, UCB/CSD-93-778 / ACM CSUR 1994

### Bibliographic record — H/P

Peter M. Chen, Edward K. Lee, Garth A. Gibson, Randy H. Katz, David A. Patterson, **“RAID: High-Performance, Reliable Secondary Storage.”**

- Technical Report UCB/CSD-93-778, November 1993.
- Berkeley archival record: <https://www2.eecs.berkeley.edu/Pubs/TechRpts/1993/6306.html>
- Period PDF mirror used for text inspection: <https://www.pdl.cmu.edu/PDL-FTP/RAID/computin.pdf>
- Later journal publication: _ACM Computing Surveys_ 26(2), June 1994, pp. 145–185.

This is a period technical synthesis by core RAID researchers. It is especially valuable here because it moves beyond the level taxonomy into implementation state, crash behavior, stale-data prevention, and reconstruction.

### §3.5 — data/parity are not the whole necessary state — H/P

The source states that a correct/reliable disk-array implementation needs state beyond data and parity, including:

- which disks have failed;
- how much of a failed disk has been reconstructed;
- which sectors are currently being updated.

It calls this non-user-data, non-parity information `meta state`.

**Anchor:** §3.5 `Implementation Considerations`, PDF pp. 29–30 in the inspected rendering.

**Grounded consequence:** reconstruction progress and current failure/update state are first-class retained control state rather than retrospective bookkeeping added by this repository.

### §3.5.1 — invalid/valid state prevents stale data — H/P

The source requires:

1. logical sectors corresponding to a failed disk be marked invalid before a request that would normally access the failed disk;
2. a reconstructed logical sector on a spare be marked valid before writes to that logical location are serviced.

The article explicitly explains that these restrictions prevent stale data from reaching users and discusses keeping the valid/invalid bit vector on stable storage.

**Anchor:** §3.5.1 `Avoiding Stale Data`, PDF p. 30.

**Grounded consequence:** physical readability does not authorize a failed/intermittently working member to answer as current state.

### §3.5.2 — parity physical presence is not enough after a crash — H/P

The source says interrupted writes can leave parity inconsistent. Unless the implementation knows which parity sectors were being updated, all parity may need regeneration after a crash. It therefore describes logging each parity sector’s consistent/inconsistent state to stable storage, marking relevant parity inconsistent before writes, and regenerating inconsistent parity after restart.

**Anchor:** §3.5.2 `Regenerating Parity after a System Crash`, PDF pp. 31–32.

**Grounded consequence:** `parity exists` and `parity is currently safe reconstruction evidence` are separate facts.

### §3.5.3 — operating with a failed disk is not the end of repair — H/P

The source explicitly labels a section `Operating with a Failed Disk` and describes that state as risky. It gives `demand reconstruction` as one method:

- requires stand-by spare disks;
- an access to a parity stripe with an invalid sector immediately reconstructs the appropriate data onto a spare;
- a background process scans the whole array so that all contents of the failed disk are eventually reconstructed within an acceptable time period.

**Anchor:** §3.5.3, PDF p. 32.

**Grounded consequence:** request-level availability after failure and completed restoration of redundancy are distinct completion states.

### §3.5.3 — parity sparing changes where data/parity roles live — H/P

The same section describes `parity sparing` for a system without stand-by spare disks. An invalid sector is reconstructed and relocated into its corresponding parity sector; relocation must be recorded as additional meta state. When the failed disk is eventually replaced, the relocated sector is copied to the spare/replacement, parity regenerated, and the relocation mark removed.

**Anchor:** §3.5.3, PDF pp. 32–33.

**Grounded consequence:** repair can temporarily change the encoded layout and thereby create new currentness/placement state before returning to the ordinary redundancy organization.

### Reliability section — reconstruction exposes a time-dependent risk interval — H/P/E

The reliability discussion immediately before §3.5 treats multiple/correlated disk failures and unrecoverable bit errors during reconstruction as threats to parity-protected arrays. It warns against idealized reliability calculations that omit implementation-specific failure interactions.

**Anchor:** §3.4 reliability discussion, especially §3.4.6 and the text immediately preceding §3.5.

**Engineering reconstruction:** a one-member failure can leave data logically available while the system occupies a more fragile interval until repair restores redundancy. The source establishes the mechanism; `degraded retention margin` is the project’s comparison term.

## Cross-case consequences admitted by this evidence

### 1. `parity redundancy ≠ replica multiplicity`

Ouchi directly supplies a reconstruction relation where a missing contribution is derived from several surviving segments plus a check sum. This is not merely “another copy somewhere.”

### 2. `single-failure service continuity ≠ restored redundancy margin`

Chen et al.’s demand reconstruction serves affected stripes and separately performs a full background reconstruction. The first successful read/write after failure is therefore not evidence that the array has returned to its previous failure-tolerance condition.

### 3. `redundant bytes physically present ≠ usable current redundancy`

Parity can become inconsistent across an interrupted write. Its currentness/consistency relation matters independently of its material survival.

### 4. `reconstruction progress can be constitutive retention meta state`

The source explicitly names how much of the failed disk has been reconstructed as state that must be accurately maintained across crashes.

### 5. `spare capacity ≠ stored payload, but can be retention infrastructure`

A stand-by spare has no current user payload before reconstruction, yet its availability changes how quickly degraded reconstructability can be converted back into repaired physical redundancy.

### 6. `encoded recoverability ≠ one surviving embodiment`

The failed contribution can be absent at its old location and absent as a complete duplicate elsewhere, yet remain recoverable because the surviving group constrains what the missing contribution must be.

### 7. `RAID nomenclature ≠ invention priority for parity recovery`

The Berkeley paper establishes a historically important name/taxonomy. Ouchi’s earlier mechanism prevents the repository from converting that terminology event into a universal invention claim.
